## 4. Diagnóstico, aprendizaje y cambio de rumbo

**Causa principal acreditada:** los dos proveedores Overpass devolvieron un fallo aguas arriba (último diagnóstico termina en HTTP 502), presentado correctamente como HTTP 503 por el endpoint. Los tests simulados y un workflow verde **no eliminan el fallo real**. El mismo run consultó una revisión antigua (`fbbe22b`), por lo que no atribuir automáticamente esos errores al código `d517ce63` hasta repetir la prueba contra el SHA publicado.

**Patrón de estancamiento:** múltiples ejecuciones dedicadas a saneamiento de campos, pruebas auxiliares y cambios documentales sin evidencia de empresas reales obtenidas. **El cuello de botella sigue siendo 1) adquirir una empresa legítima y 2) completar con ella auditoría → scoring → borrador → propuesta en el navegador publicado**. El botón con countdown mejora usabilidad, pero no desbloquea la cadena comercial.

**Aprendizaje operativo persistente:**
1. Un smoke exitoso que admite 503 sólo valida que el fallo se muestra honestamente, no la búsqueda. Contar como PASS de negocio únicamente un registro real, con URL de fuente/licencia y continuación del flujo.
2. Dos fallos consecutivos de una misma estrategia obligan a cambiar de fuente/flujo, no a volver a ajustar sólo timeout, mensajes de error o sanitización.
3. La versión ensayada y la versión de producción deben coincidir explícitamente; registrar SHA en cada evidencia.
4. No bloquear el primer vertical slice por integraciones IA, auth/db o Lighthouse: siguen como limitaciones declaradas, pero no sustituyen una prueba con datos reales.
